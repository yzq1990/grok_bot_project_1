# Multi-Agent 协作项目集

从 Grok Bot 多 Agent 工作台截图梳理出的**可执行**项目说明。先落地 README，后续按需拆分支与 PR。

## 这是什么

一套「中控 + 专精 Agent」协作规范与三条可推进主线：

| 编号 | 项目 | 状态 | 可否立刻开干 |
|------|------|------|----------------|
| P1 | Orchivane × Grok Bot 落地与上游贡献 | 规划中 | 是（文档/Skill/试点） |
| P2 | Codex 第 6 版候选包核验与放行 | 门禁中 | 是（有明确包与清单） |
| P3 | REA 逆向工程工作台 | 搭建中 | 部分（先通加载与派发） |

详细说明见仓库内 `docs/`（若尚未推送，以本 README 为准）。

## 强制状态词典

每个交付物**只设一个负责人**。状态必须分句、可核验：

| 状态 | 含义 | 谁宣布 |
|------|------|--------|
| 做完了 | 实现/撰写完成 | 该交付物唯一负责人 |
| 测过了 | 独立核验通过 | 审核官或书面指定验收人 |
| 推上去了 | 已进入共享仓库/发布通道 | 技术官或发布角色 |
| 上线了 | 对使用者或生产环境生效 | 首席执行官或书面授权人 |

禁止：「都弄好了」「冰哥同意了」「差不多能发」等口头合并表述。口头转述**不算授权**。

## P1 — Orchivane × Grok Bot（可做）

**背景：** Orchivane（约 v0.4.1，MIT）是面向 Codex / Claude Code 的 Skill 文档集（1 总说明 + 7 章节），不是 Grok Bot 安装包。理念与「CEO + 专精 Agent」同构。

**可立即执行：**

1. 抽取上游文档 → 写成 Grok Bot Skill（`skills/orchivane-grok-bot/`）。
2. 审核官按本 README 状态词审过 → 标「测过了」。
3. 用真实任务试点（建议挂靠 P2 状态汇报模板）并留日志。
4. 撰写《Grok Bot 实现指南》，以笔名「大冰」向 Orchivane 提 PR（须基于真实使用，非错别字修补）。

**不做：** 伪造使用数据；强行 1:1 拷贝 Codex/Claude 指令。

**Done：** Skill 可加载 + 试点日志 + PR 材料齐备。

## P2 — Codex 第 6 版放行（可做）

**输入线索：** 候选包 `第6版_候选包_源码可核_1647.zip`（约 41 文件），含 md5 / diff / 测试；三处必改已宣称落实；本阶段**不加新功能**。

**核验清单（复制即用）：**

- [ ] 文件数与清单一致；路径 → md5 可复算  
- [ ] diff 仅覆盖约定必改项 + 声明内测试  
- [ ] Swift / iOS 等相关改动有测试或手工记录  
- [ ] 审核官书面「测过了」（非口头）  
- [ ] 分别登记：做完了 → 测过了 → 推上去了 → 上线了  

**交付物建议：** `CHECKSUMS.md` · `DIFF_SUMMARY.md` · `TEST_REPORT.md` · `RELEASE_GATE.md`

**Done：** 审核关闭且完成「推上去了」（上线另记）。

## P3 — REA 工作台（部分可做）

**可立即执行：**

1. `REA_LOAD_CHECKLIST.md`：路径、依赖、自检步骤。  
2. MCP / 工具连通性日志（失败不得标「做完了」）。  
3. `DISPATCH_MATRIX.md`：任务类型 → 聊天页 / Agent（禁止口头改派）。  
4. 最小样本跑通「做完了 → 测过了」。

**边界：** 仅授权目标；合规外利用类工作不在范围。

**Done：** 可稳定加载 + 有派发矩阵 + 一份报告模板闭环。

## 建议顺序

1. **P2** 门禁（时间紧、输入明确）  
2. **P3** 轻量打通（额度紧张时给 P2 让路）  
3. **P1** 用 P2/P3 真实日志满足上游「真实使用」后再提 PR  

```text
P2 放行 ──► 真实门禁日志 ──► P1 Orchivane PR
P3 加载/派发 ─────────────▲
```

## 贡献约定

- 一个 PR / 一个交付物 / 一个负责人。  
- PR 描述里写清当前状态词；合并前至少「测过了」。  
- 临近发布节点只修必改，不夹带功能。
